## IAC-02 ECS 관리 책임 분리

### 작업과 범위

- `다음 진행하자` 요청에 따라 이전 CICD-01 후속 상태와 TASKS의 선행 조건을 확인했다. PORT-01의 환경·인증·예산·보존 조건이 미정이므로 독립 착수 가능한 IAC-02의 로컬 구현·검증을 수행했다.
- ECS service에 `ignore_changes = [task_definition, desired_count]`를 추가했다. Terraform은 서비스 최초 생성·인프라·task definition 템플릿·scaling 정책, CD는 실행 revision, Application Auto Scaling은 생성 후 task 수를 관리한다. 기존 IAC-02의 관리 책임 분리 범위를 구현했으며 신규 기술 채택·중요 결정의 승인 기록을 만들지 않았다.
- 모듈과 dev 환경에 템플릿 ARN 출력을 추가했다. 현재 CD가 생성한 family의 최신 revision과 Terraform 템플릿을 구분할 수 있다. 변수 설명과 Terraform 실행 진입점도 맞췄다.
- [구조](../DESIGN.md#ecs-배포와-스케일링-책임)와 [배포 기준](../design/DEPLOYMENT.md#ecs-관리-책임과-배포-순서-iac-02)에 최초 배포, 템플릿 변경 후 명시적 설정 배포, service 재생성, AWS 검증 절차를 반영했다. 현재 CD는 서비스의 revision을 복제하므로 Terraform의 CPU·환경변수 변경이 workflow 재실행만으로 전달되지 않는 한계를 명시했다.
- 초기 1 task 안내는 Auto Scaling min capacity도 1로 맞추도록 보완했다. 운영 예산이나 실제 scaling 범위를 새로 확정한 것은 아니다.

### 검증 조건·명령·결과

- 도구: `/tmp/aws-migration-iac-tools/terraform`의 Terraform 1.9.8. 기존 lock 기준 AWS provider 5.100.0, archive provider 2.8.0을 사용했다. 저장소를 `/tmp/aws-migration-iac-check/terraform`에 복사하고 `terraform -chdir=/tmp/aws-migration-iac-check/terraform/environments/dev init -backend=false -input=false -no-color`로 로컬 검증 환경을 준비했다. 도구·provider 다운로드 외 AWS API 호출은 수행하지 않았다.
- `/tmp/aws-migration-iac-tools/terraform fmt -check -recursive terraform`: 통과.
- 복사한 최신 코드에서 `terraform -chdir=/tmp/aws-migration-iac-check/terraform/environments/dev validate -no-color`: 통과. 실제 state backend 초기화·AWS plan/apply 성공을 뜻하지 않는다.
- Plan 실험은 실제 ECS service 리소스 블록을 추출하고 의존 리소스 참조를 상수로 치환한 임시 fixture를 사용했다. 합성 state에는 외부 배포 revision `:7`, task 수 3, 구성에는 템플릿 revision `:1`, 초기 task 수 1을 넣었다. 실제 계정·인증정보·데이터는 사용하지 않았다. Provider는 fixture 자격값과 `skip_credentials_validation`, `skip_requesting_account_id`, `skip_metadata_api_check`를 사용했다.
- `python3 /tmp/aws-migration-iac-tools/verify-plan.py`로 `terraform plan -refresh=false -input=false -no-color -out=<case>.tfplan`과 `terraform show -json <case>.tfplan` 결과를 비교했다. 스크립트·합성 state·plan은 `/tmp/aws-migration-iac-check/service/` 및 도구 디렉터리의 임시 산출물이다.

| 실험 | 판정 |
| --- | --- |
| 기존 service update plan | revision `:7`·task 수 3 유지, 태그 변경은 update로 감지 |
| State 없는 create plan (`-state=nonexistent.tfstate`) | 구성의 revision `:1`·초기 task 수 1 사용 |
| 같은 fixture에서 ignore 목록을 비운 비교 plan | revision `:1`·task 수 1로 되돌리는 변경 발생 |

- 초기 합성 state에서 `scheduling_strategy` 기본값을 생략해 service 교체가 계획되었다. Fixture에 `REPLICA` 등 provider 기본값을 채워 기존 service 갱신 조건으로 수정한 뒤 위 판정을 확인했다. 이는 시험 데이터 불완전으로 발생했으며 실제 AWS 장애 관찰이 아니다.

### 한계·정리·문서 대조

- 실제 CD 배포·Auto Scaling 변경 후 AWS refresh plan/apply와 설정 배포·롤백은 수행하지 않았다. 합성 state plan은 Terraform의 lifecycle 동작을 확인하며 AWS와의 통합 동작을 보증하지 않는다. IAC-02는 AWS 실행 검증 대기로 유지한다.
- AWS 리소스 생성·삭제·배포·부하·장애 주입을 수행하지 않았다. 실제 원격 state, GitHub workflow·권한 설정을 변경하지 않았다. 로컬 임시 산출물은 `/tmp`에만 두었다.
- TASKS의 IAC-02 수용 기준, DESIGN의 관리 책임, DEPLOYMENT의 실행 순서, Terraform 코드·변수·출력, README와 PROGRESS를 대조했다. 코드의 두 속성 제외 범위와 문서가 일치한다. 템플릿 변경이 자동 배포되지 않는 영향과 재생성 시 초기값 사용을 문서에 명시했다. 실제 AWS plan/apply 증빙은 남아 있다.
- PRD·API·DB 계약·기존 결정·Day별 완료 표기를 변경하지 않았다. 이 변경은 AWS 배포 관리 보강이므로 사용자 API 기능 변경을 CHANGELOG에 추가하지 않았다. 현재 작업일지 링크를 이 파일로 갱신했다.
- 최종 검증: Terraform fmt/validate를 통과했고 저장소 Markdown 상대 링크 147개의 대상 파일·앵커 오류는 0개다. `git diff --check`를 통과했다.

## 파일 서비스 개선 작업 등록

### 작업과 근거

- 파일 서비스 아키텍처 평가 후 사용자의 작업 등록 요청에 따라 [TASKS](../TASKS.md#파일-서비스-정합성과-장애-처리)에 FILE-01~04를 추가했다. 업로드 객체·DB 정합성, 캐시 장애와 삭제 일관성, 검사 상태 연결을 P1로, S3 업로드 스트리밍을 P2로 등록했다. 모두 예정이며 Java 전환·서비스 분리·특정 메시지 시스템 채택을 승인한 것으로 기록하지 않았다.
- 코드 관찰: `FileService.upload`는 객체 저장 후 DB 저장을 수행하며 실패 보상 경로가 없다. `RedisFileMetadataCache`는 조회·무효화 실패가 호출자에게 전달될 수 있고, `FileService.findVisible`은 조회한 메타데이터를 다시 캐시에 기록한다. 동시 삭제·조회 시 오래된 값 재삽입 가능성은 코드에서 도출한 위험이며 실행으로 재현한 결과가 아니다.
- 코드 관찰: 업로드 직후 DB 상태는 `AVAILABLE`·`CLEAN`이며 Lambda는 S3 태그를 기록하고 DB·캐시를 갱신하지 않는다. 확장자 가드를 실제 백신 검사로 취급하지 않았다. S3 업로드는 `inputStream.readAllBytes()`로 전체 파일을 버퍼링한다. 동시 업로드의 실제 메모리 영향은 아직 측정하지 않았다.
- 각 작업에 선행 조건·실패 주입 및 경합 시나리오·수용 기준·관련 기준 문서를 명시했다. 실패 복구 과정에서 정상 파일 또는 논리 삭제로 보존한 파일을 정리하지 않는 조건, 검사 이벤트 중복·역순·DB 저장 전 도착·삭제 경합도 포함했다.
- 기존 OPS-01은 FILE-02 결과를 재사용하도록 연결하고, FILE-04의 전체 부하 측정은 PERF-01, 전송 경로 비교는 ARCH-01의 범위로 유지했다. VERIFY-01/02의 기준선 기록과 개선 후 재검증을 구분하고 TASKS의 권장 순서·PROGRESS의 다음 작업을 맞췄다.

### 검증 범위와 문서 대조

- PRD의 파일 상태·논리 삭제 정책, API의 현재 업로드 상태 설명, AWS의 실제 백신·DB 동기화 한계, VALIDATION의 캐시 장애 설명을 작업 수용 기준과 대조했다. 현재 동작과 목표의 차이는 작업으로 등록했으며 기준 계약·승인 결정·기존 Day 이력은 변경하지 않았다.
- 이번 변경은 작업 등록과 연결 문서 갱신이다. 애플리케이션·Terraform 코드를 추가 변경하지 않았고 테스트·장애 주입·성능 측정·AWS 실행은 수행하지 않았다. 중요한 설계 선택은 작업 착수 시 기준 문서와 대조하고 합의할 범위로 남겼다.
- 검증 결과: 저장소 Markdown 상대 링크 164개의 파일·앵커 오류 0개, 전체 작업 ID 21개 중복 없음, 신규 4개 모두 예정 상태 및 신규 작업 간 선행 관계 비순환을 확인했다. `git diff --check`를 통과했다. 기존 Day 완료 표기·IAC-02/CICD-01의 실행 검증 대기 상태는 유지했다.

## 아키텍처 레퍼런스 페이지 추가

- 사용자 요청에 따라 백엔드 패키지 import 관계, `build.gradle`, 프로필 설정, `docker-compose.yml`, nginx 설정, `terraform/environments/dev/main.tf`, CI/CD workflow, Lambda handler를 읽고 아키텍처 설명을 [architecture-overview.html](../assets/architecture-overview.html)로 저장했다. [자산 목록](../assets/README.md)에 연결했다.
- 페이지는 현재 작업 트리의 코드 관찰 요약이며 DESIGN·DECISIONS의 기준 계약을 바꾸지 않는다. Lambda의 실제 백신·DB 동기화는 후속 범위로 표기했다.
- 코드 관찰로 `auth.application → auth.api`(서비스가 API DTO 사용)와 `*.application → config.security.AuthUserPrincipal` 의존을 계층 규칙 예외로 기록했다. 개선 작업으로 등록하거나 결정으로 반영하지 않았다.
- 사용자가 제공한 비교 그림을 바탕으로 패키지·계층 절에 도메인과 JPA Entity 분리(현재 구현)·통합(비교안) 흐름도와 장단점을 추가했다. 분리 방식은 `FileService.delete`의 `markDeleted()` 후 `save()` 호출과 `JpaFileMetadataRepositoryAdapter`의 `from()`·`toDomain()` 변환으로 확인했다. 통합 방식은 채택 결정이 아닌 비교 설명이다.
- 애플리케이션·Terraform 코드는 변경하지 않았고 테스트·AWS 실행은 수행하지 않았다. 브라우저 렌더링 확인은 하지 않았다.

## 계층 경계 개선 작업 등록

- 아키텍처 페이지에 기록한 계층 규칙 예외 2건을 사용자 요청으로 [TASKS](../TASKS.md#완료된-작업)에 LAYER-01(P2)·LAYER-02(P3, 선택)로 등록했다. 둘 다 예정이며 실행 오류가 아닌 구조 정리 작업이다.
- 코드 관찰: `AuthService.signup`은 `SignupRequest`를 받고 `login`은 `LoginResponse`를 반환하며 `user.api.UserResponse`를 사용한다. `login`의 입력은 이메일·비밀번호 문자열이다. `FileService`는 `AuthUserPrincipal`의 사용자 ID·역할만 읽으며 이 레코드의 `authorities()`가 Spring Security 타입을 반환한다. `UserService`는 이미 사용자 ID만 받는다.
- API·DB 계약, 기존 결정, Day 이력은 변경하지 않았다. 코드 변경과 테스트는 수행하지 않았다. TASKS의 권장 순서와 PROGRESS의 다음 작업에 연결했다.
- 아키텍처 페이지의 예외 설명 중 "`LoginRequest`를 직접 받는다"는 표현은 위 관찰과 다르며, 수정은 LAYER-01 수용 기준의 페이지 갱신 또는 별도 요청으로 남겼다.

## LAYER-01/02 계층 경계 정리 구현

### 변경

- LAYER-01: `AuthService.signup`은 이메일·비밀번호·이름 값을 받고, `login`은 새 `auth.application.LoginResult`(사용자·토큰·토큰 유형·만료 초)를 반환한다. `LoginResponse`·`UserResponse` 변환은 `AuthController`로 옮겼다. `AuthService`의 `auth.api`·`user.api` import를 제거했다.
- LAYER-02: `common.actor.Actor`(사용자 ID·관리자 여부)를 추가했다. `AuthUserPrincipal.toActor()`가 역할 `ADMIN`을 관리자로 변환하고, `FileController`가 이를 `FileService`에 넘긴다. `FileService`의 `config.security` import를 제거했다. 권한 판단 규칙(소유자 또는 관리자)은 그대로다.
- API 요청·응답 형식, 오류 코드, DB 스키마는 바꾸지 않았다. `AuthService`가 `JwtTokenProvider`(config.security)를 쓰는 것은 토큰 발급 기능 의존이므로 범위 밖으로 두었다.
- [아키텍처 페이지](../assets/architecture-overview.html)의 계층 예외 표기를 해소 내용으로 갱신했다.

### 검증

- 도구: 시스템에 Java가 없어 Eclipse Temurin 17.0.21을 세션 임시 디렉터리에 받아 `JAVA_HOME`으로 지정했다. Gradle wrapper 8.10.2가 배포본을 내려받았다. Docker가 없어 PostgreSQL·Redis·MinIO 실서버 검증은 하지 않았다.
- 변경 전 기준선 `./gradlew test --no-daemon`: 9개 통과.
- 변경 후 같은 명령: 기존 9개와 새 `FileServiceAccessTests` 3개(역할→`Actor` 변환, 소유자·관리자 조회 허용과 다른 사용자 거부, 다른 사용자 삭제 거부와 관리자 삭제 후 조회 불가) 모두 통과. 기존 통합 테스트에 관리자 경로가 없어 단위 테스트로 보완했다.
- `grep`으로 `*/application/`에서 `auth|user|file.api`와 `AuthUserPrincipal` import가 없음을 확인했다.

## FILE-01/02/04/05 구현

### 합의

- FILE-01: 사용자가 객체를 먼저 저장하는 방식을 유지하되 저장 응답 유실·DB 쓰기 반복 실패 등 여러 실패를 고려하자고 했다. 실패 상황 표를 정리했고, 사용자가 멱등성 키 구현을 요청해 함께 진행했다. 결정은 [DEC-002](../DECISIONS.md#결정-목록)에 기록했다.
- FILE-05: 사용자가 Redis 대신 DB에 키를 두는 가용성 문제를 물었다. 업로드가 이미 DB에 의존하므로 새 의존성이 없다는 분석과 오류 코드·보관 기간 제안 후 "멱등성키 구현하자"로 승인했다. [ADR-001](../adr/001-UPLOAD-IDEMPOTENCY-KEY.md), [DEC-001](../DECISIONS.md#결정-목록).
- FILE-02: 사용자가 캐시 무효화 재시도와 비동기 재시도·사용자 알림을 제안했다. 재시도만으로는 오래된 값 재삽입 경쟁을 막지 못한다는 점, 사용자 알림 대신 운영자 로그·지표를 쓰는 안을 설명했고 사용자가 권장안 진행을 승인했다. [DEC-003](../DECISIONS.md#결정-목록).

### 변경

- 저장소 포트를 `allocate`(위치 확정)·`write`(크기·Content-Type 지정 스트림)·`load`·`delete`·`list`로 바꾸고 Local·MinIO·S3 adapter를 맞췄다. S3의 `readAllBytes()` 버퍼링을 `RequestBody.fromInputStream(size)`로, MinIO의 크기 미지정 스트림을 크기 지정으로 바꿨다 (FILE-04).
- 업로드를 `FileUploadService`로 분리했다. 메타데이터 기록 3회 재시도, 기록 없음이 확인될 때만 보상 삭제, 확인 불가 시 객체 보존, 커밋 후 응답 유실 시 저장된 값 반환을 구현했다. `UploadRecorder`가 `files` 저장과 `upload_requests` 완료를 한 트랜잭션으로 묶는다 (FILE-01).
- `Idempotency-Key`와 `upload_requests` 테이블(InMemory·JPA adapter), 오류 코드 `IDEMPOTENCY_IN_PROGRESS`(409, `Retry-After`)·`IDEMPOTENCY_KEY_MISMATCH`(422), `Idempotent-Replayed` 헤더, 만료 기록 정리 작업을 추가했다. 완료·실패 전환은 저장 위치가 같을 때만, 재시작은 `version`이 같을 때만 반영한다 (FILE-05).
- 관리자 API `GET /api/admin/storage/orphans`, `POST /api/admin/storage/orphans/cleanup`과 `files.storage_path` 인덱스를 추가했다 (FILE-01).
- 캐시: Redis 오류 시 DB 우회, Lua 버전 비교 쓰기, 삭제 시 키 삭제 대신 `deleted` 상태 덮어쓰기, 즉시 2회·백그라운드 7회 재시도와 `file.cache.update.failures` 지표를 구현했다. 다운로드·삭제는 DB에서 상태를 읽고, 캐시 적중 시 다시 쓰지 않는다 (FILE-02).
- 문서: [API](../design/API.md), [DATABASE](../design/DATABASE.md), [DESIGN](../DESIGN.md), [VALIDATION](../design/VALIDATION.md), [TROUBLESHOOTING](../TROUBLESHOOTING.md), [DECISIONS](../DECISIONS.md), [ADR-001](../adr/001-UPLOAD-IDEMPOTENCY-KEY.md), [CHANGELOG](../CHANGELOG.md), [TASKS](../TASKS.md), [PROGRESS](../PROGRESS.md), [백엔드 안내](../../backend/README.md), [아키텍처 페이지](../assets/architecture-overview.html)를 갱신했다.

### 한계와 남은 확인

- Redis Lua 스크립트의 버전 비교는 실제 Redis에서 실행하지 않았다. 다중 인스턴스 경합 재현도 미수행이다 (FILE-02 실제 Redis 검증 대기).
- 유니크 제약·조건부 갱신은 H2 PostgreSQL 모드로만 확인했다. 실제 PostgreSQL·Aurora의 `ddl-auto=update`로 `upload_requests`가 생성되는지와 동시 요청은 미확인이다 (FILE-05).
- MinIO adapter 변경은 컴파일만 확인했다. MinIO·S3 실서버의 크기·해시 일치와 변경 전후 메모리·오류율 측정은 미수행이다 (FILE-04).
- 409 응답의 `Retry-After` 헤더는 HTTP 통합 테스트로 확인하지 않았다. 고아 객체 점검은 저장소 전체를 한 번에 나열한다.
- AWS 리소스·Compose 실행·배포는 하지 않았다. 기존 Day 이력과 FILE-03 범위는 바꾸지 않았다.

### 관찰과 한계

- V-ADMIN-02를 위해 `.env`의 `APP_FILE_IDEMPOTENCY_IN_PROGRESS_TIMEOUT`을 `PT1M`으로 바꿨다가 검증 후 `PT15M`으로 되돌리고 backend를 다시 만들었다(컨테이너 환경변수 `PT15M` 확인).
- 캐시 version은 메모리의 `Instant`를 마이크로초로 버림하고 PostgreSQL은 반올림해, DB에서 다시 읽은 값의 version이 1 클 수 있다(관찰값 …160 → …161). 같은 상태를 다시 쓰는 경우라 오래된 값 거부에는 영향이 없다.
- backend를 하나만 띄워 FILE-02의 다중 인스턴스 무효화 실패는 재현하지 않았다. AWS 확인(S3·Aurora·ElastiCache)은 아직이다.
- 검증 스크립트는 세션 임시 디렉터리에서 실행했고, 첫 실행에서 작업 폴더를 옮긴 뒤 `docker compose`가 설정 파일을 찾지 못해 V-DATA 명령이 실패했다. `--project-directory`를 지정해 다시 실행한 결과를 위 표에 적었다. 문서의 명령은 저장소 루트 기준이라 해당하지 않는다.
- 스택은 실행 중으로 두었다. 검증 데이터는 사용자 3명, 파일 8건(약 12MB), 업로드 요청 3건이다.
