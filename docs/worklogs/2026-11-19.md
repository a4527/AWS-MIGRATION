## V-LOC-02~05 실행

### 작업과 근거

- 사용자 요청으로 PORT-01 잔여인 [V-LOC-02~05](../design/VALIDATION.md#7a-aws-배포-전-로컬-검증)를 실행했다. 2026-11-18에 막혔던 Docker는 이번에 WSL에서 동작했다(Docker 29.9.2, Compose v5.6.1).
- 온프레미스 스택을 `docker compose up --build -d`로 띄우고 V-ONP-01 확인(actuator `UP`, 테이블 `files`·`upload_requests`·`users`) 뒤 진행했다. [0. 공통 준비](../design/VALIDATION.md#0-공통-준비)의 함수·변수와 V-LOC의 `DC`·`AWS_LOCAL_BUCKET`(`fileshare-local`)을 셸에 불러 썼다.

- V-LOC-03 통과. uid `10001`, `cpus=500000000 mem=1073741824 oom=false restarts=0`, V-LOC-02 이후 메모리 320.9MiB / 1GiB(CPU 0.35%), 컨테이너 내부 `GET /api/health` `HTTP/1.1 200`.
- V-LOC-04 4-1 통과. postgres 20초 pause 중 로그인이 17.8초 만에 토큰을 받았다.
- V-LOC-04 4-2 실패(현재 코드의 한계 확인).

## 기동 중 DB 미가용 대응 결정

### 작업과 근거

- 4-2 결과를 보고하고 대응 세 가지(배포 전 DB 깨우기, 최소 ACU 상향, 기동 시 DB 재시도 설정)를 제시했다. 사용자가 "db를 먼저 깨우는 방식"을 선택해 [DEC-010](../DECISIONS.md#결정-목록)으로 기록했다.
- 깨우는 방법: DB가 database subnet에 있어 로컬에서 연결할 수 없다. AWS 블로그 [Introducing scaling to 0 capacity with Amazon Aurora Serverless v2](https://aws.amazon.com/blogs/database/introducing-scaling-to-0-capacity-with-amazon-aurora-serverless-v2/)는 연결 요청(실패 포함), RDS Data API 요청, 로그 파일 조회·다운로드, 설정 변경을 재개 조건으로, 재개 시간을 15초 미만으로 안내한다. Data API는 켜져 있지 않아 로그 목록 조회(`describe-db-log-files`)를 골랐다.
- 시점: 실습 계층을 새로 만들면 ECR이 비어 task가 4.6 배포에서 처음 뜬다. 자동 일시정지는 300초(`aurora_seconds_until_auto_pause` 기본값)라 workflow 시작 시점이 아니라 ECS 배포 단계 직전에 깨우도록 했다. 실행 중인 task가 있으면 연결이 유지돼 일시정지되지 않는다고 보고 생략 조건으로 적었다.

### 변경

- [VALIDATION V-LOC-04](../design/VALIDATION.md#v-loc-04-db-재개-지연): 4-2를 컨테이너 ID 직접 시작, 40초 pause, 시각 기록, Hikari 시작 시각 확인으로 고치고, 현재 기대 결과를 종료(exit 1)로 적었다.
- [DEPLOYMENT 4.6](../design/DEPLOYMENT.md#46-github-actions-배포-실행): 배포 전 DB 깨우기 절차와 판정을 추가했다.
- [MIGRATION 주의 사항](../design/MIGRATION.md#주의-사항)에 온프레미스와 다른 점으로 한 줄 추가했다.
- [TROUBLESHOOTING](../TROUBLESHOOTING.md#ecs-task가-기동-중-db-연결-실패로-종료됨), PROGRESS, TASKS(PORT-01·MIG-02), AGENTS.md의 현재 작업일지 링크를 갱신했다.

### 한계

- AWS 호출은 하지 않았다. `describe-db-log-files`로 실제 재개되는지, 재개 이벤트 문구, 깨우기를 빠뜨렸을 때 ECS 다음 task가 성공하는지는 MIG-02에서 확인한다.
- pause는 Aurora 재개를 흉내 낸 것이다. Aurora에서 연결이 재개 완료까지 기다리는지, 6초 안에 실패하는지는 로컬에서 알 수 없다.
- 애플리케이션 코드는 바꾸지 않았다. 다른 이유로 DB가 기동 중 잠시 안 될 때(예: Aurora 장애 조치)도 task는 같은 방식으로 종료되고 ECS 교체에 맡긴다.

## 원격 state (IAC-01)

### 작업과 근거

- 사용자가 IAC-01 → SEC-01 순서 진행을 요청했다. 잠금은 S3 자체 잠금(`use_lockfile`), state bucket은 별도 Terraform(`terraform/bootstrap`)으로 만들기로 선택했다([DEC-011](../DECISIONS.md#결정-목록)).
- Terraform 1.17.2, AWS provider 5.100.0. 두 계층 `required_version`을 `>= 1.11.0`으로 올렸다.

### 변경

- `terraform/bootstrap/`: state bucket(버전 관리, SSE-S3, 퍼블릭 차단, `BucketOwnerEnforced`, TLS 외 접근 거부 정책, `prevent_destroy`, 이전 버전 만료(최신 20개 초과·90일), 미완료 multipart 7일, 만료된 delete marker 정리). 로컬 state. 실제 bucket 이름과 Owner 값은 gitignore된 `terraform.tfvars`에만 있다.
- 두 계층: `backend.tf`(key `fileshare/<계층>/terraform.tfstate`, `use_lockfile`, `encrypt`)를 커밋 대상으로 두고 bucket은 gitignore된 `backend.hcl`로 넘긴다. `backend.tf.example`을 지우고 `backend.hcl.example`을 추가했다. `.gitignore`에 `backend.hcl`.
- [DEPLOYMENT 4.1-1](../design/DEPLOYMENT.md#41-1-원격-state-준비-iac-01)(bootstrap·init·잠금 해제·버전 복구), 4.3 init 명령, [Terraform 안내](../../terraform/README.md#개발-환경-실행), [AWS 계층 설명](../design/AWS.md#유지-계층과-실습-계층), DECISIONS, TASKS, PROGRESS.

### 검증 조건·명령·결과

- bootstrap: plan 7개 생성 → apply 성공 → 재 plan 변경 없음. 이후 delete marker 정리 규칙 추가 apply(1개 변경). 실제 설정 조회: 태그에 Owner 있음, 버전 관리 `Enabled`, `AES256`, 퍼블릭 차단 4개 `True`, lifecycle 규칙 2개. TLS 없는 익명 GET은 403(익명 거부와 구분되지 않아 TLS 정책의 근거는 아니다). `Project=fileshare` Owner 누락 0개.
- dev-data 이전: 이전 전 로컬 state serial 28·리소스 21개. `terraform init -migrate-state -force-copy -backend-config=backend.hcl` 성공. 원격 state는 리소스 21개이고 `.resources`가 원본과 같았다(serial 1, lineage는 새 값). `terraform plan -detailed-exitcode` exit 0.
- 잠금 경합: plan A 실행 중 `.tflock` 객체를 확인하고 plan B(`-lock-timeout=0s`)를 실행 → `Error acquiring the state lock`, `StatusCode: 412`, A의 ID·`OperationTypePlan` 표시, B exit 1. A는 정상 종료(변경 없음). `terraform console`은 잠금을 오래 잡지 않아 경합 재현에 쓰지 못했다.
- 남은 잠금 복구: plan 실행 중 프로세스를 `kill -9`로 종료 → `.tflock` 남음 → 다음 plan이 412로 실패 → `terraform force-unlock -force <ID>` → 잠금 객체 삭제, plan exit 0. (첫 시도에서 `pkill -f` 패턴이 명령을 실행한 셸까지 맞아 셸이 함께 종료됐다. 남은 단계를 따로 실행했다.)
- 버전 복구: 최신 VersionId로 state를 내려받아 `terraform show`로 확인. 같은 serial로 `state push`하자 `cannot overwrite existing state with serial 1 with a different state that has the same serial`로 거부됐다(내려받은 파일 52197바이트, 원격 객체 52196바이트). `-force`로 push → 새 버전 생성(버전 2개), serial 2, 리소스 21개, plan 변경 없음.
- 세 디렉터리 `terraform fmt -check -recursive`, `validate` 통과. dev는 backend init만 했고 state가 없다(`No state file was found`).

### 정리·한계

- dev-data의 0바이트 로컬 `terraform.tfstate`는 지웠다. 이전 사본 `terraform.tfstate.backup`·`terraform.tfstate.pre-iac01`은 권한 600으로 남겼다. 비밀값이 평문으로 들어 있어, 원격 state로 문제없이 작업한 뒤 지운다.
- 이전 버전 복구는 내용이 같은 버전으로만 시험했다. 실제로 낮은 serial을 되돌린 뒤 import·apply로 맞추는 과정은 하지 않았다.
- 접근 권한은 단일 IAM user라 사람·CI별로 나누지 않았다. CI가 Terraform을 실행하게 되면(IAC-03) state bucket 권한을 따로 정한다.
- dev 계층 원격 state의 실제 쓰기·잠금은 MIG-02 apply에서 확인한다.

## SEC-01 선택 사항 논의

- 사용자가 비밀값 저장소로 SSM Parameter Store SecureString을 선택했다(Secrets Manager·RDS 관리 비밀번호 대신, 비용 $0).
- provider 5.100.0 스키마에서 write-only 속성(`aws_rds_cluster.master_password_wo`, `aws_ssm_parameter.value_wo`, `aws_secretsmanager_secret_version.secret_string_wo`)과 ephemeral 리소스(`aws_ssm_parameter`, `aws_secretsmanager_random_password`)를 확인했다.
- "Terraform이 처음 한 번 생성, write-only로 state·tfvars·plan에 값 없음, `*_wo_version`을 올릴 때만 교체, 값은 SSM에서 조회 가능"을 설명했다. 이 방식의 최종 동의는 아직 받지 않았다. 코드 변경 없음.

## 개인 계정 백업 준비

### 작업과 근거

- 사용자가 부트캠프 계정이 리소스를 가끔 지운다며 유지 계층만 개인 계정으로 옮기는 교차 계정 구성을 물었다. 실행 중 교차 계정(C)·전부 이전(D)·한 계정 유지(A)·개인 계정으로 백업만(B)을 비교했고, 사용자는 DB·객체 손실 대비로 백업만 보내는 쪽에 관심을 보였다. 비교와 권장안(S3 교차 계정 복제 + `pg_dump`)은 [제안](../proposals/CROSS-ACCOUNT-BACKUP.md)에 남겼다. 미승인이다.
- 확인한 사실: Aurora가 `aws/rds` 관리 키로 암호화되어 스냅샷을 다른 계정에 바로 공유할 수 없다.

### 개인 계정 CLI 접근

- 사용자가 개인 계정 콘솔에서 IAM user `fileshare-backup-admin`(콘솔 접근, MFA, `SignInLocalDevelopmentAccess`, role 맡기 inline policy), 권한 정책(`fileshare-backup-*` bucket 관리), role `fileshare-backup-bucket-admin`(trust: 그 user + `aws:MultiFactorAuthPresent`)을 만들었다. 콘솔의 "AWS 계정" 신뢰 엔티티(`:root`, 계정 전체 위임) 대신 user를 지정한 사용자 정의 trust policy를 썼다.
- 로컬 `~/.aws/config`에 `personal`(aws login), `personal-backup`(`role_arn`+`source_profile`+`mfa_serial`), `personal-backup-tf`(`credential_process`)를 추가했다. 계정 ID·ARN은 저장소에 넣지 않았다.
- 경과:
  - `aws login --profile personal`: WSL에서 브라우저가 열리지 않아 Windows 브라우저로 URL을 열어 완료.
  - MFA 없이 assume → `AccessDenied`(기대). `!` 프롬프트에서는 MFA 코드 입력 불가.
  - 별도 터미널에서 MFA 코드를 넣어도, `--serial-number`·`--token-code`를 직접 줘도 `AccessDenied`. `aws login` 세션 문제로 판단해 access key로 바꿨으나 같은 오류가 나 판단이 틀렸음을 확인했다(키 인증·WSL 시계 정상).
  - 실제 원인: role 이름이 `fileshare-backup-bucket-admin`인데 inline policy `Resource`와 `role_arn`이 `fileshare-backup-admin-role`이었다. 사용자가 inline policy를 고치고 로컬 `role_arn`을 맞춘 뒤 성공.
  - 사용자 요청으로 `aws login`으로 되돌렸다. 로컬 `[personal]` access key를 지웠고(콘솔의 키 비활성화·삭제는 사용자 몫), 이전 access key 세션으로 맡은 role 캐시가 MFA를 건너뛰게 해 `~/.aws/cli/cache`의 해당 파일을 지웠다. 별도 터미널에서 MFA 코드를 넣어 `aws login` 세션 + MFA로 role을 맡는 것을 사용자가 확인했다.
- 권한 범위 확인(role 세션): `list-buckets` 허용(0개), `fileshare-backup-` 밖 이름의 `create-bucket` 거부, `iam list-users` 거부. `personal-backup-tf`도 같은 role ARN.

### 변경

- [제안 문서](../proposals/CROSS-ACCOUNT-BACKUP.md)와 [제안 목록](../proposals/INDEX.md), PROGRESS 다음 작업, [TROUBLESHOOTING](../TROUBLESHOOTING.md#assumerole이-정책이-맞아-보이는데도-accessdenied)(AssumeRole 거부, MFA 입력 실패, role 캐시, WSL 브라우저).

### 한계

- 개인 계정에는 아직 리소스를 만들지 않았다. 백업 구성은 제안 합의 후 SEC-01 → MIG-02 다음에 한다.
- `personal-backup`은 1시간마다 별도 터미널에서 MFA 코드를 다시 넣어야 한다.

## 개인 계정 백업 채택

- 사용자가 [제안](../proposals/CROSS-ACCOUNT-BACKUP.md)의 권장안(B + B-2: S3 교차 계정 복제 + `pg_dump`)을 채택했다. [DEC-012](../DECISIONS.md#결정-목록)와 [ADR-002](../adr/002-CROSS-ACCOUNT-BACKUP.md)에 기록했다. 조직 밖 계정으로 데이터 사본이 나가는 데이터 경계 결정이라 ADR로 남겼다.
- TASKS에 BACKUP-01(2단계, P1)을 등록하고 OPS-02 선행에 연결했다. 제안 목록·PROGRESS·[AWS 계층 설명](../design/AWS.md#유지-계층과-실습-계층)에 승인된 미구현으로 반영했다. 구현·AWS 변경은 하지 않았다.
- SEC-01의 Terraform 생성·write-only 방식은 여전히 확인 대기다.
