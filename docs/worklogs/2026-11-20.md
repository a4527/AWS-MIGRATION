## SEC-01 비밀값 주입

### 결정

- 2026-11-19에 확인 대기로 남았던 방식에 사용자가 동의했다. Terraform이 ephemeral `random_password`로 값을 만들고 write-only 인자로만 보낸다. 기존 Aurora 비밀번호는 새 값으로 교체한다. JWT secret parameter는 실습 계층(`dev`)에 둔다. 기록은 [DEC-013](../DECISIONS.md#결정-목록)에 있다.
- 확인한 사실:
  - provider 5.100.0 소스(`internal/service/rds/cluster.go`): `master_password`를 config에서 빼도 값이 없으면 `MasterUserPassword`를 보내지 않는다. `master_password_wo_version`이 바뀔 때만 write-only 값을 보낸다. `master_password_wo`와 `master_password`는 함께 쓸 수 없다(`ConflictsWith`).
  - ECS 문서: 같은 리전 SSM parameter는 `secrets[].valueFrom`에 ARN으로 지정하고, execution role이 task 시작 때 읽는다. 값을 교체해도 실행 중인 task에는 반영되지 않는다.
- 추정(미확인): AWS 관리 키 `aws/ssm`으로 암호화한 parameter는 execution role에 `kms:Decrypt`가 없어도 읽힌다. MIG-02에서 task가 처음 기동할 때 확인한다.

### 변경

- `modules/aurora`: `master_password` → `master_password_wo`(ephemeral 변수) + `master_password_wo_version`.
- `dev-data`: random provider(`>= 3.7`)를 추가했다. ephemeral 비밀번호(40자, 특수문자는 `-_`만 사용)를 만들어 SSM `/<project>/<env>/aurora/master-password`(SecureString, `value_wo`)와 Aurora에 같은 apply에서 쓴다. 변수는 `aurora_master_password_version`(기본 1)이고 output으로 parameter 이름을 낸다. `$`·`{`는 Spring placeholder로 해석될 수 있어서, `@`·`/`는 JDBC URL과 Aurora 제약 때문에 뺐다.
- `dev`: ephemeral JWT secret(영숫자 64자)을 만들어 SSM `/<project>/<env>/app/jwt-secret`에 쓴다(`app_jwt_secret_version`). DB 비밀번호 ARN은 `aws_caller_identity`·`aws_partition`으로 이름에서 만든다. data source를 쓰면 값이 state에 들어가기 때문이다. `aurora_master_password`·`app_jwt_secret` 변수를 없앴다.
- `modules/ecs`: 환경변수에서 `DB_PASSWORD`·`APP_JWT_SECRET`을 빼고 `secrets`로 옮겼다. execution role에 두 ARN만 대상으로 하는 `ssm:GetParameters` inline policy를 붙였고, ECS service가 이 policy에 의존하도록 했다.
- tfvars: 두 example 파일을 갱신했다. 실제 `terraform.tfvars`(gitignore 대상)에서는 비밀값 두 줄씩을 지웠다. 이 값은 교체 뒤 쓸 수 없게 된다.
- 문서: DEPLOYMENT(환경변수 설명, 4.1-1, 4.2, 새 4.2-1 비밀값 관리, 설정 배포 3단계), AWS.md(계층 설명, ECS 환경변수, Secret 처리 기준, 변수 목록, apply 전 확인, 현재 한계), terraform README, DECISIONS(DEC-013), TASKS(SEC-01), PROGRESS, AGENTS(현재 작업일지 링크).

### 검증

- `terraform fmt`, 두 계층 `validate` 통과. 오프라인 사본에서 실행했다(backend 제외, random 3.9.1 설치).
- mock provider plan 테스트(`terraform test`, 사본에만 둔 테스트 파일과 테스트용 output):
  - dev: 컨테이너 `environment`에 `DB_PASSWORD`·`APP_JWT_SECRET`이 없다. `secrets`가 DB 비밀번호 ARN(`arn:aws:ssm:us-east-1:<account>:parameter/fileshare/dev/aurora/master-password`)과 JWT parameter ARN을 가리킨다. JWT parameter는 SecureString이다. 통과.
  - dev-data: parameter 이름이 실습 계층 규칙과 같고 SecureString이다. Aurora·SSM의 write-only 버전이 모두 1이다. 통과.
  - mock은 구성 연결만 확인한다. state에 값이 없는지는 실제 plan JSON·state로 확인해야 한다.
- 정적 권한 점검:
  - CI 배포 role trust: `aud = sts.amazonaws.com`(StringEquals). `sub = repo:<repo>:ref:refs/heads/<branch>`는 StringLike지만 와일드카드가 없어 정확히 일치할 때만 허용된다.
  - PassRole: ECS task·execution role 두 개만, `iam:PassedToService = ecs-tasks.amazonaws.com` 조건이 있다. `RegisterTaskDefinition`은 리소스 수준 권한을 지원하지 않아 `*`다.
  - SSM 읽기: execution role만 가능하다. task role·Lambda·CI role에는 SSM 권한이 없다.
  - CD workflow는 실행 중인 revision을 복제하므로 `secrets`(ARN)를 유지한다. runner의 `task-definition.json`에 평문 비밀값이 더는 없다.

### 한계와 미수행

- 처음에는 AWS에 접근할 수 없었다. `terraform init`이 STS `InvalidClientTokenId`로 실패했다. 아래 [AWS 인증 전환과 적용](#aws-인증-전환과-적용)에서 해결하고 적용했다.
- 남은 위험: main에서 workflow를 실행할 수 있는 사람은 execution role을 쓰는 task definition을 등록해 비밀값을 로그로 내보낼 수 있다. 배포 권한 자체에 따르는 위험이라 CICD-02의 환경 승인으로 줄인다.
- SEC-01 이전 state 버전(S3 원격 state 이력)과 `dev-data/terraform.tfstate.backup`·`.pre-iac01`에는 이전 비밀번호가 평문으로 남아 있다. 적용 때 비밀번호를 교체하므로 쓸 수 없는 값이 된다. 로컬 사본은 적용을 확인한 뒤 지운다.

## AWS 인증 전환과 적용

### 인증 전환

- `default` 프로필의 키 `AKIA…B5V6`는 `aws sts get-access-key-info` 결과 부트캠프 계정(끝자리 3881)의 키였다. `iam list-access-keys`로 보니 해당 user에 키가 0개였다. 키가 삭제된 것이고, 정리 정책이 지운 것으로 추정한다(미확인).
- 사용자가 부트캠프 계정도 `aws login`으로 바꾸자고 했다([DEC-014](../DECISIONS.md#결정-목록)). 사용자가 `bootcamp`·`personal` 두 프로필에 로그인했고, 각각 끝자리 3881·2813임을 확인했다.
- `default`를 `credential_process`로 바꾸고 `~/.aws/credentials`를 비우는 명령은 권한 검사(파괴적 동작)에서 거부됐다. 그래서 `~/.aws/config`에 `bootcamp-tf`(`credential_process`) 프로필만 추가하고 `AWS_PROFILE=bootcamp-tf`로 실행했다. 삭제된 키는 아직 `~/.aws/credentials`의 `[default]`에 남아 있다.
- 사용자가 콘솔에서 Aurora가 안 보인다고 했다. 조회해 보니 us-east-1에 `fileshare-dev-aurora`·`fileshare-dev-aurora-1`이 `available`, 삭제 보호 켜짐이었다. 자동 스냅샷 1개(11-19)와 자동 백업(`active`)도 있었다. 서울(ap-northeast-2)·us-east-2·us-west-2에는 클러스터가 없었다. 콘솔 리전이 달랐던 것으로 판단한다.

### AWS 적용

- 유지 계층 `init`: random 3.9.1 설치, aws 5.100.0 유지. `plan -out`: 1개 추가(`aws_ssm_parameter.aurora_master_password`), 1개 변경(Aurora: `master_password` → null, `master_password_wo_version = 1`), 삭제 0.
- plan JSON: 두 리소스의 `after`에서 `master_password_wo`·`value_wo`·`value`·`master_password`가 모두 null이다. `before`에는 이전 비밀번호가 있다(state에 있던 값, 이번에 교체됨).
- 저장한 plan으로 apply 성공(3분 20초).
- 확인:
  - `state pull`: Aurora `master_password = ""`, `master_password_wo_version = 1`. SSM `value = ""`, `has_value_wo = true`, `value_wo_version = 1`, SecureString.
  - SSM의 새 값(40자)이 state 문자열에 0번 나온다. 값은 출력하지 않았다.
  - 재 plan `-detailed-exitcode` = 0(변경 없음).
  - RDS 이벤트: `Initiated resume ... due to database background activity`(01:55:37Z) → `Successfully resumed`(01:55:49Z, 약 12초) → `Reset master credentials`(01:58:37Z).
- 확인하지 못한 것: SSM 값으로 실제 DB 접속이 되는지. DB가 database subnet에 있어 로컬에서 접속할 수 없다. MIG-02 첫 task 기동으로 확인한다. 일시정지 상태에서 apply가 재개를 일으켰고 재개에 약 12초 걸렸다. MIG-02의 재개 소요 측정에 참고한다.
