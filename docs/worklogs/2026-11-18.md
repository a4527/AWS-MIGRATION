## PORT-01·MIG-01 결정

### 작업과 근거

- `다음 진행하자` 요청에 따라 [PROGRESS](../PROGRESS.md)의 다음 작업인 PORT-01·MIG-01을 확인했다. 두 작업 모두 사용자 결정이 필요해 인증 방식, 리전·예산, 데이터 이전 방식을 질문했다.
- 사용자 선택: 인증은 IAM Identity Center(SSO), 리전은 us-east-1이고 실습 계층은 바로 지운다. MIG-01은 A(데이터 이전 없음)로 정했다. 기록은 [DEC-006](../DECISIONS.md#결정-목록), [DEC-007](../DECISIONS.md#결정-목록)에 있다.
- 사용자가 "DB와 스토리지는 남겨야 하는데 비용이 얼마인지, RDS나 다른 서비스가 나은지" 물었다. us-east-1 월 비용 비교표를 제시했다. 출처는 서드파티 가격 자료(bytebase, vantage, selfhost.dev 등)와 AWS RDS PostgreSQL 가격 페이지 링크다. 공식 가격 페이지 수치는 직접 확인하지 않았다(관찰이 아닌 추정).
  - S3 12MB: $0.01 미만. Aurora 0.5 ACU 상시: 약 $44. Aurora 0 ACU 자동 일시정지: 스토리지만(몇 센트). RDS db.t4g.micro 상시: 약 $14, 중지 시 약 $2.3(7일 후 자동 재시작). 스냅샷만 남기는 방식: 몇 센트, 복원 10분 이상.
- 사용자가 "S3와 Aurora Serverless 자동 일시정지로 스토리지만 사용"을 선택해 [DEC-008](../DECISIONS.md#결정-목록)로 기록했다. Aurora를 그대로 쓰므로 DEC-004의 대상 구성은 바뀌지 않는다.
- 예산 금액·알림 수신처는 사용자가 정하지 않아 PORT-01 잔여로 남겼다. WSL에는 `aws` CLI와 `terraform`이 설치되어 있지 않다(`command not found`).

## Terraform 계층 분리

### 변경

- `terraform/environments/dev-data`를 새로 만들었다. 유지 계층으로 `vpc`, `s3`, `aurora` 모듈을 호출한다. AWS provider는 `>= 5.80, < 6.0`(lock 5.100.0)이다.
- `terraform/environments/dev`는 실습 계층이다. vpc·s3·aurora 모듈 호출을 지우고 `data.tf`에서 VPC·subnet(Tier 태그)·private route table·Aurora SG·Aurora cluster·S3 bucket을 이름으로 조회한다. subnet ID는 정렬해 쓴다. 새 `nat` 모듈(EIP·NAT·private 기본 경로)을 호출하고, ECS는 `depends_on = [module.nat]`로 둔다.
- `modules/vpc`: NAT·EIP와 private route table의 인라인 기본 경로를 제거했다. `private_route_table_id`를 출력한다. 인라인 `route`를 생략한 route table은 Terraform이 경로를 관리하지 않으므로 `nat` 모듈의 `aws_route`와 충돌하지 않는다.
- `modules/aurora`: Aurora SG를 직접 만든다(규칙 없음). `min_capacity = 0`일 때만 `seconds_until_auto_pause`를 설정한다. 기본값은 `deletion_protection = true`이고 최종 스냅샷 `<prefix>-aurora-final`을 남긴다.
- `modules/security-groups`: Aurora SG를 제거하고 `aws_vpc_security_group_ingress_rule`로 유지 계층 Aurora SG에 `5432 from application SG`를 붙인다.
- 기본 리전을 us-east-1로 바꿨다. Terraform 변수·예시, `.github/workflows/backend-ci-cd.yml`의 `AWS_REGION`, `application-s3.yml`의 기본값(ECS는 환경변수로 주입), DEPLOYMENT·VALIDATION 예시가 대상이다.
- AWS에 apply한 적이 없어 state 이동(`moved`/`import`)은 필요 없다.

### 검증 조건·명령·결과

- 도구: 체크섬을 확인한 Terraform 1.9.8을 세션 scratchpad에 내려받았다. 저장소를 scratchpad로 복사해 실행했다. AWS 자격 증명이 없어 AWS API 호출은 없다.
- `terraform fmt -recursive`: 처음에는 정렬 차이 2개 파일이 있었고, 저장소에 적용한 뒤 통과했다.
- `dev-data`·`dev` 각각 `init -backend=false` 후 `validate`: 둘 다 통과했다.
- 복사본에 테스트 전용 output을 추가하고 `mock_provider "aws"`로 `terraform test`(plan)를 실행했다.
  - `dev-data` 2건 통과: 기본값에서 `min_capacity = 0`, `seconds_until_auto_pause = 300`, `deletion_protection = true`, `skip_final_snapshot = false`, 최종 스냅샷 식별자를 확인했다. `aurora_min_capacity = 0.5`일 때 `seconds_until_auto_pause`가 null인 것도 확인했다.
  - `dev` 2건 통과: data source(override)의 subnet이 정렬되는 것, bucket·Aurora endpoint 연결, NAT가 정렬 후 첫 public subnet을 쓰는 것을 확인했다. plan 그래프에서 `module.nat`의 EIP·NAT·route와 `module.security_groups.aws_vpc_security_group_ingress_rule.aurora_from_application`을 확인했다.
  - 테스트 파일과 테스트 전용 output은 scratchpad 복사본에만 두었고 저장소에 넣지 않았다.
- 문서 상대 링크·앵커 점검은 아래 문서 대조에 적었다.

### 한계

- mock provider plan은 구성 연결만 확인한다. 실제 AWS에서 확인할 것은 MIG-02로 넘겼다. Aurora 16.6에서 0 ACU가 허용되는지, 일시정지·재개 시간, data source 조회, 실습 계층 destroy 후 유지 계층 plan이 변경 없음인지 등이다.
- `dev-data`에서 `terraform plan`을 실제로 실행하지 않았다. 처음 시도는 자격 증명이 없어 IMDS 조회 단계에서 실패했다.
- 백엔드 설정 기본값(`AWS_REGION`)만 바꿨고 백엔드 테스트는 다시 실행하지 않았다.
- 가격은 서드파티 자료 기준 추정이다. 실제 청구는 PORT-01 예산 알림과 Cost Explorer로 확인한다.

## PORT-01 예산·Owner 태그·도구 설치

### 작업과 근거

- 사용자 지시: 예산 월 $10, 알림 이메일 지정, 도구 설치 위임, "모든 리소스나 서비스는 태그로 Owner를 붙여야 하고 아니면 삭제될 수 있다". 이메일과 Owner 값은 문서에 쓰지 않고 gitignore된 `terraform.tfvars`(권한 600)에만 넣었다. [DEC-009](../DECISIONS.md#결정-목록)에 기록했다.
- 도구 설치(sudo 없음, 사용자 경로):
  - Terraform 1.17.2: releases.hashicorp.com의 SHA256SUMS로 체크섬을 확인하고 `~/.local/bin`에 설치했다.
  - aws-cli 2.41.0: AWS 문서 페이지에서 공개키를 받아 서명을 확인했다(Good signature, 지문 FB5D B77F D5C1 18B8 0511 ADA8 A631 0ACC 4672 475C). `~/.local/aws-cli`에 설치하고 링크는 `~/.local/bin`에 두었다.
- 코드 변경:
  - 두 계층에 필수 `owner` 변수를 추가하고 provider `default_tags`와 `common_tags`에 Owner를 넣었다. `common_tags`에서는 마지막에 넣어 `tags`의 Owner를 덮어쓴다. 예시 tfvars의 `Owner = "portfolio"`는 제거했다.
  - 태그 전파: ECS service `propagate_tags = "SERVICE"`·`enable_ecs_managed_tags`, Aurora `copy_tags_to_snapshot`.
  - CD workflow: 현재 task definition을 `--include TAGS`로 읽고 jq로 태그를 합쳐 새 revision에 붙인다. Owner가 없으면 실패한다. deploy role에는 `ecs:CreateAction = RegisterTaskDefinition` 조건으로 `ecs:TagResource`를 추가했다.
  - 유지 계층에 `aws_budgets_budget`을 추가했다. 월 $10이고, 실제 비용 50/80/100%와 예측 100%에서 이메일로 알린다. 기본 비용 필터는 `TagKeyValue user:Owner$<owner>`다.
- 로컬 `terraform.tfvars` 두 개를 만들었다. Aurora 비밀번호(32자), JWT secret(64자), bucket 이름 접미사는 Python `secrets`로 생성했다. 출력하거나 기록하지 않았다. GitHub repository는 origin remote 값이다. 비용을 줄이려고 로컬 tfvars의 ECS desired·min은 1로 두었다.

### 검증 조건·명령·결과

- Terraform 1.17.2: `fmt -recursive`를 적용한 뒤 두 계층 `validate`가 통과했다.
- 오프라인 plan(scratchpad 복사본): 가짜 자격 증명과 provider `skip_*` 설정으로 AWS 호출 없이 실행했다. 실습 계층의 data source는 고정값으로 바꿨다. `plan -refresh=false`의 JSON에서 생성되는 리소스의 `tags_all.Owner`를 확인했다.
  - `dev-data`: 태그 가능한 17개 모두 Owner가 있다. 누락 0.
  - `dev`: 태그 가능한 32개 모두 Owner가 있다. 누락 0.
  - 태그 속성이 없는 타입: route table association, S3 하위 설정 4종, `aws_appautoscaling_policy`, `aws_ecr_lifecycle_policy`, IAM policy attachment, Lambda permission, `aws_route`, S3 notification.
  - 확인한 planned 값: 예산 10.00 USD MONTHLY, 필터 `user:Owner$<owner>`, 알림 4개(수신자 각 1). Aurora는 `copy_tags_to_snapshot = true`, `min_capacity = 0`, auto pause 300초. ECS service는 propagate SERVICE, managed tags true, desired 1.
  - 비밀값이 들어 있는 plan 파일과 복사된 tfvars는 확인 뒤 삭제했다.

### 한계

- AWS에 로그인하지 않아 실제 plan/apply, 예산 생성 권한, Owner 비용 할당 태그 활성 상태는 확인하지 않았다. Owner가 활성 비용 할당 태그가 아니면 필터 때문에 예산이 $0으로 보인다. 확인 명령은 [AWS 배포 4.4](../design/DEPLOYMENT.md#44-terraform-apply)에 적었다.
- workflow 변경은 GitHub에서 실행하지 않았다. 태그를 합친 JSON을 deploy action이 그대로 등록하는지는 첫 CD 실행에서 확인한다.
- 공유 계정에 GitHub OIDC provider(`token.actions.githubusercontent.com`)가 이미 있으면 실습 계층 생성이 충돌할 수 있다. apply 때 확인한다.
- 원격 state bucket·lock table(IAC-01)도 만들 때 Owner 태그를 붙여야 한다.

### 문서 대조

- 갱신한 문서: DECISIONS(DEC-009), TASKS(PORT-01), PROGRESS, design/AWS(공통 태그), design/DEPLOYMENT(4.0 조건표, 4.2 변수, 4.4 확인 명령), terraform/README. 사용자 기능 변경이 없어 CHANGELOG는 갱신하지 않았다.

## 인증 변경과 유지 계층 실제 plan

### 작업과 근거

- 사용자가 SSO 대신 access key 방식으로 바꾸자고 했고, `aws configure`로 로그인을 마쳤다. DEC-006, DEPLOYMENT 4.0·4.1, TASKS, PROGRESS의 인증 표기를 access key로 고쳤다. 계정 ID와 IAM 사용자 이름은 문서에 적지 않았다.
- `aws sts get-caller-identity`가 성공했다. 주체는 IAM user이고 기본 리전은 us-east-1이다.

### 검증 조건·명령·결과

- `dev-data`에서 `terraform init`(로컬 state) 후 `terraform plan` 실행: `Plan: 27 to add, 0 to change, 0 to destroy`. plan JSON에서 태그를 지원하는 생성 리소스 중 Owner 누락은 0이다. 예산은 10.00 USD이고 Owner 태그 필터가 있다. Aurora는 min 0, max 2, auto pause 300초, 삭제 보호, 최종 스냅샷, 스냅샷 태그 복사, 암호화가 켜져 있다.
- `aws rds describe-db-engine-versions`: us-east-1의 aurora-postgresql 16.x에는 `16.6-limitless`만 있고 일반 16.6이 없다. 이대로 apply하면 실패하므로 기본값을 16.15로 바꿨다. 온프레미스가 `postgres:16`이라 같은 메이저를 유지했다. `describe-orderable-db-instance-options`로 16.15에서 `db.serverless`가 가능한 것을 확인했다. 다시 실행한 plan도 27개 생성이다.
- `aws ce list-cost-allocation-tags`: `AccessDeniedException`이 났다(linked account에는 비용 할당 태그 접근 권한이 없음). Owner 태그 활성 여부를 직접 확인할 수 없다.
- 기존 예산은 다른 사용자 것 2개다(필터 없음, 이번 달 계정 전체 실제 비용 약 $24). Owner 필터를 빼면 공유 계정 전체 비용이 잡혀 $10 예산이 바로 초과되므로 필터를 유지한다.
- GitHub OIDC provider(`token.actions.githubusercontent.com`)는 계정에 없다. 실습 계층 생성 시 충돌 위험이 없다.

### 한계

- 아직 apply하지 않았다. 사용자 승인 뒤 실행한다.
- Owner가 payer 계정에서 비용 할당 태그로 활성화되어 있지 않으면, 예산이 계속 $0으로 보이고 알림도 오지 않는다. 조직 관리자에게 확인해야 한다.

## AWS 배포 전 로컬 검증 시나리오

### 작업과 근거

- 사용자가 apply 전에 로컬 테스트를 먼저 하자고 했다. 온프레미스 시나리오(V-ONP~V-ADMIN)는 이미 통과했으므로, AWS에서만 타는 경로를 골라 [V-LOC-01~06](../design/VALIDATION.md#7a-aws-배포-전-로컬-검증)을 작성했다. 대상은 `s3` 프로필의 AWS SDK 경로, Fargate 자원 한도와 health 경로, Aurora 재개 지연, Lambda 핸들러, CD 태그 병합이다.
- `docker-compose.aws-local.yml`을 추가했다. backend를 ECS와 같은 프로필(`postgres,redis,s3`)과 0.5 CPU·1GiB로 띄운다. S3 요청은 SDK 표준 환경변수 `AWS_ENDPOINT_URL_S3`로 MinIO에 보낸다(코드 변경 없음). SDK가 가상 호스트 방식으로 요청하므로 MinIO에 `MINIO_DOMAIN`과 `<bucket>.minio` alias를 준다. 자격 증명은 MinIO 계정이고 사용자 `~/.aws`는 쓰지 않는다.
- Aurora 0 ACU 재개는 PostgreSQL 컨테이너 `pause`로 흉내 낸다(DEC-008 위험 확인). ElastiCache TLS, IAM task role, ALB·NAT는 로컬에서 재현하지 않는다고 시나리오에 적었다.

### 검증 조건·명령·결과

- V-LOC-01: Temurin 17.0.21+9를 scratchpad에 받았다(Adoptium API 체크섬 OK). `./gradlew test --no-daemon` 결과 48개 통과(실패·오류·건너뜀 0). `terraform fmt -check -recursive` 통과, 두 계층 `validate` 통과, `dev-data` plan은 `27 to add`.
- V-LOC-06: 시나리오의 jq를 그대로 실행했다. 태그가 있으면 `family`와 태그 2개가 유지되고 `pass`, 태그가 없거나 Owner가 빈 값이면 `refuse`.
- 문서 링크: VALIDATION.md의 상대 링크와 앵커 오류 0.

### 한계

- WSL에서 `docker` 명령이 없어(Docker Desktop WSL 연동 꺼짐) V-LOC-02~05는 실행하지 않았다. compose override(MinIO 가상 호스트, SDK checksum 헤더 호환)와 pause 재현 방식은 실행 전까지 가정이다.
