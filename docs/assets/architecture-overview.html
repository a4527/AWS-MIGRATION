파일 공유 API의 온프레미스 기준선(로컬 WSL2 + Docker Compose)과 애플리케이션 내부 구조를 정리한 페이지입니다. 애플리케이션은 도메인별 패키지 안을 계층으로 나누고, 저장소·DB·캐시는 인터페이스(포트) 뒤에 숨겨 Spring 프로필로 구현체를 바꿉니다. 같은 이미지가 AWS에서도 프로필만 바꿔 돌아갑니다.

2 · Compose 실행 흐름

docker compose up --build -d 한 번에 일어나는 일

저장소 루트의 .env(비밀번호·JWT secret)를 읽어 아래 순서로 올라옵니다. 순서는 depends_on 조건이 정합니다.

1 · buildbackend 이미지 빌드backend/Dockerfile: eclipse-temurin:17-jdk에서 bootJar → 17-jre에 jar만 복사
2 · pull나머지 이미지 받기postgres 16, redis 7, Bitnami MinIO, nginx 1.27
3 · create네트워크·볼륨기본 네트워크 1개, 볼륨 postgres-data·redis-data·minio-data
4 · wait데이터 계층 준비postgres·redis healthcheck 통과, minio 시작
5 · startbackend → nginxJPA ddl-auto: update로 테이블 생성, nginx가 8080으로 받기 시작

멈추기와 지우기

docker compose down: 컨테이너와 네트워크만 지웁니다. 볼륨이 남아 다시 올리면 사용자·파일이 그대로입니다.

docker compose down -v: 볼륨까지 지웁니다. DB 행과 MinIO 객체가 모두 사라집니다.

검증 도구

객체 저장 확인: docker compose --profile tools run --rm mc "mc ls local/files"

수동 시험 화면: http://localhost:8080/test/ (nginx만 제공, AWS에는 없음)

3 · 요청 처리

요청 하나가 지나가는 길

Spring Boot 4.1.3(Spring Security 7) 기준 실제 클래스 이름입니다. 세션 없이(STATELESS) 요청마다 JWT를 검증합니다.

  1. RequestLoggingFilter가장 먼저 실행(HIGHEST_PRECEDENCE). 유효한 X-Request-Id를 쓰거나 새로 만들어 MDC requestId와 응답 헤더에 넣고, 끝나면 http.access 접근 로그(메서드·경로 패턴·상태·durationMs)를 남김
  2. SecurityConfigCSRF 끔, 세션 없음. /api/health·/actuator/health·/api/auth/signup·/api/auth/login은 공개, 나머지는 인증 필요
  3. JwtAuthenticationFilterUsernamePasswordAuthenticationFilter 앞에서 Bearer 토큰을 JwtTokenProvider로 검증하고 AuthUserPrincipal을 SecurityContext에 넣음
  4. RestAuthenticationEntryPoint · RestAccessDeniedHandler토큰 없음·만료는 401 AUTH_INVALID_TOKEN, 권한 부족은 403 AUTH_ACCESS_DENIED를 ApiResponse 형식으로
  5. ControllerFileController·UserController·AuthController·AdminStorageController. DTO 검증(@Valid) 후 principal.toActor()로 보안 타입을 Actor로 바꿔 서비스에 넘김
  6. ServiceFileUploadService(업로드·멱등성·보상), FileService(목록·조회·다운로드·삭제), UserService, AuthService. 소유자 또는 ADMIN 권한 판단
  7. 포트FileStorage, FileMetadataRepository, UploadRequestRepository, FileMetadataCache, UserRepository
  8. 어댑터MinioFileStorage, Jpa*RepositoryAdapter → Spring Data JPA, RedisFileMetadataCache(Lua 버전 비교)
  9. ApiResponse성공은 {success, data, message}로 감싸 응답
  10. GlobalExceptionHandlerBusinessException → ErrorCode의 상태(진행 중 멱등 요청은 Retry-After), 크기 초과 → FILE_TOO_LARGE, 입력 검증 → 400 VALIDATION_ERROR, 그 밖 → 500
API경로비고
인증POST /api/auth/signup, POST /api/auth/loginBCrypt, JWT 발급. 토큰 갱신·로그아웃 미구현
사용자GET/PATCH /api/users/me, GET /api/users/{id}다른 사용자 조회는 ADMIN만
파일POST /api/files, GET /api/files?size&cursor, GET /api/files/{id}, GET /api/files/{id}/download, DELETE /api/files/{id}목록은 커서 페이지(size 기본 20·최대 100, 응답 {items, nextCursor}, PERF-02·DEC-024)

도메인과 JPA Entity 분리

이 프로젝트는 도메인 모델(FileMetadata)과 JPA Entity(FileMetadataEntity)를 별도 클래스로 둡니다. 아래 그림은 현재 방식과, 하나로 합쳤을 때의 흐름을 삭제(markDeleted()) 기준으로 비교합니다.

분리 (현재 구현)

도메인이 JPA 애노테이션·지연 로딩을 모르기 때문에 같은 Service가 InMemory 저장소(기본·테스트)와 JPA 저장소(postgres 프로필)를 그대로 씁니다.

대가: FileMetadataEntity.from()·toDomain() 매핑 코드가 필요하고, 변경 감지 대신 save()를 호출해야 합니다.

통합 (비교안)

클래스와 매핑 코드가 줄고, 트랜잭션 안의 상태 변경이 변경 감지로 자동 저장됩니다.

대가: 도메인 규칙이 JPA 생명주기에 묶여 프로필별 저장소 교체와 순수 단위 테스트가 어려워집니다.

5 · 의존성

계층 간 의존 방향

실제 import 기준입니다. 실선은 사용, 점선은 구현(implements)입니다. 어댑터는 Spring 프로필이나 app.storage.type 속성으로 하나만 빈으로 등록됩니다.

도메인 모듈 간 관계

auth──▶user file─ ✕ ─user

AuthService는 user.domain과 user.repository를 직접 씁니다. file은 user를 import하지 않고 ownerId(Long)로만 소유자를 구분합니다.

서비스는 API DTO를 모름 (LAYER-01)

AuthService는 회원가입 값을 받고 LoginResult(사용자·토큰·만료)를 반환합니다. LoginResponse·UserResponse 변환은 AuthController가 합니다.

서비스는 보안 타입을 모름 (LAYER-02)

컨트롤러가 AuthUserPrincipal.toActor()로 common.actor.Actor(사용자 ID·관리자 여부)를 만들어 FileService에 넘깁니다.

7 · 업로드 흐름

파일 업로드 (온프레미스)

메타데이터 조회는 캐시 → DB 순서로 찾은 뒤 소유자 또는 ADMIN인지 확인합니다. 다운로드와 삭제는 캐시를 쓰지 않고 DB 상태로 판단합니다. 삭제는 상태를 DELETED로 바꾸는 논리 삭제이고, 캐시에는 삭제 상태를 덮어씁니다. Redis가 응답하지 않으면 DB로 우회합니다. 목록(GET /api/files)은 (owner_id, id) 인덱스로 최신순 한 페이지만 읽습니다.

  1. Clientmultipart/form-data로 POST /api/files 요청. 재전송 대비 Idempotency-Key 헤더 선택
  2. nginx/api/를 backend로 프록시. client_max_body_size 10m를 넘으면 413
  3. JwtAuthenticationFilterBearer 토큰 검증 후 AuthUserPrincipal 설정. 컨트롤러가 Actor로 변환
  4. FileUploadServiceUploadPolicy로 크기 10MiB 이하, 확장자 허용목록(pdf, png, jpg, jpeg, txt, csv) 검증
  5. FileStorage객체 위치(UUID)를 먼저 확정. 쓰기 응답이 유실돼도 정리할 수 있게 함
  6. upload_requests키가 있으면 IN_PROGRESS 기록. 완료된 같은 요청은 첫 결과 재전송, 진행 중 409 + Retry-After, 다른 요청 422
  7. MinioFileStorage크기를 아는 스트림으로 MinIO files bucket에 저장 (전체 버퍼링 없음)
  8. UploadRecorderfiles 행 저장과 요청 완료를 한 트랜잭션으로. 검사 모드 none이라 바로 available·NOT_SCANNED. 실패 시 재시도(3회), 끝내 실패하면 기록 없음 확인 후 객체 삭제, 확인 불가면 객체 보존(관리자 고아 점검 API로 정리)
  9. RedisFileMetadataCachefiles:metadata:{id}에 updatedAt 버전 비교 쓰기. 실패해도 업로드는 성공
  10. FileControllerApiResponse로 감싸서 응답. 재전송이면 Idempotent-Replayed: true 헤더
