## 배경

업로드 응답을 받지 못한 클라이언트가 다시 요청하면 같은 파일이 두 번 저장된다. 업로드는 객체를 먼저 저장하고 DB에 기록하므로, 재시도마다 객체와 메타데이터가 하나씩 늘어난다.

## 결정

- `POST /api/files`에 선택 헤더 `Idempotency-Key`를 받는다. 헤더가 없으면 기존과 같이 동작한다.
- 키 기록은 Redis가 아닌 DB `upload_requests` 테이블에 둔다. `(owner_id, idempotency_key)` 유니크 제약으로 동시 요청 중 하나만 진행시킨다.
- 객체를 쓰기 전에 `IN_PROGRESS`와 저장 위치를 기록하고, 메타데이터 저장과 같은 트랜잭션에서 `COMPLETED`로 바꾼다. 완료 처리는 해당 시도의 저장 위치가 일치할 때만 성공해 늦게 끝난 이전 시도를 롤백한다.
- 같은 요청 판단: 파일명·크기·설명·본문 SHA-256의 해시.
- 응답: 완료된 같은 요청은 첫 결과와 `Idempotent-Replayed: true`, 진행 중이면 `409 IDEMPOTENCY_IN_PROGRESS`와 `Retry-After: 5`, 다른 요청이면 `422 IDEMPOTENCY_KEY_MISMATCH`, 형식 오류는 `400 VALIDATION_ERROR`. 실패로 끝난 키는 같은 요청으로 다시 시도할 수 있다.
- 보관 기간은 24시간(`app.file.idempotency.ttl`)이며 만료 기록은 주기 작업이 지운다. 15분(`in-progress-timeout`) 넘게 진행 중인 기록은 중단된 것으로 보고 새 시도가 이어받으며, 남은 객체는 정합성 점검이 찾는다.

## 대안

- Redis 저장: 빠르고 TTL이 기본 제공되지만 Redis가 업로드의 필수 의존성이 된다. Redis 장애 시 중복 허용과 업로드 거절 중 하나를 골라야 하고, 메모리 축출·재시작으로 키가 사라지면 보장이 깨진다.
- `files` 테이블 컬럼: 테이블은 줄지만 진행 중 상태와 실패 후 재시도를 표현하기 어렵다.

## 영향

- 업로드는 이미 DB가 있어야 성공하므로 새 가용성 의존성은 없다. 키가 있는 업로드는 DB 쓰기와 본문 해시 계산이 한 번씩 늘어난다.
- API·DB 계약이 늘어난다: [API](../design/API.md#post-apifiles), [DATABASE](../design/DATABASE.md#업로드-요청-테이블).
- 키 범위는 사용자별이다. 다른 사용자가 같은 키를 써도 충돌하지 않는다.
